# Global edition: C2PA Content Credentials for generated images and video

Date: 2026-11-01 (Asia/Shanghai). Scope: the global edition (`MARKET_REGION=global`). The China edition is unchanged unless someone sets `C2PA_ENABLED=true`.
This is an engineering note, **not legal advice**. Legal should confirm that this is enough for Art. 50(2) before relying on it.

## Why

Regulation (EU) 2024/1689 Art. 50(2): providers of systems that generate synthetic audio, image, video or text must make sure the outputs are **marked in a machine-readable format and detectable as artificially generated**, using technical solutions that are effective, interoperable, robust and reliable as far as technically feasible. Before this change the global edition marked text only (visible label + `aiMetadata`); an image came back as a bare provider URL.

C2PA Content Credentials is the interoperable standard for this: a signed manifest embedded in the file that says "created by a generative AI model" (IPTC digital source type `trainedAlgorithmicMedia`) and breaks if the pixels are changed afterwards.

## What it does

`POST /api/v1/ai/generate/image` (global edition, flag on):

1. the provider returns an image URL (fal.ai, as before);
2. the API downloads the file (https only, public hosts only, redirects re-checked, 25 MiB cap, format taken from the bytes, not the header);
3. it signs a C2PA manifest into the file (JPEG, PNG, WebP, AVIF, MP4, MOV) with the configured certificate;
4. it stores the signed copy (`MEDIA_STORE_DIR`, 30 days) under an unguessable name and returns that URL;
5. the response keeps everything it had (`aiGenerated`, `aiLabel`, `aiMetadata`) and adds `providerUrl` and a `c2pa` block.

```json
{
  "url": "/api/v1/ai/media/9f2c…e1.png",
  "providerUrl": "https://v3.fal.media/files/…/out.png",
  "aiGenerated": true,
  "aiLabel": "[This content was generated by AI]",
  "aiMetadata": { "ai_generated": true, "media_type": "image", "content_id": "…" },
  "c2pa": { "standard": "C2PA", "signed": true, "signer": "configured", "digitalSourceType": "http://cv.iptc.org/newscodes/digitalsourcetype/trainedAlgorithmicMedia", "manifestInstanceId": "xmp:iid:…" }
}
```

The manifest holds: the standard `c2pa.actions` (`c2pa.created` + digital source type), claim generator `ContentFlow`, and our own assertion `org.contentflow.ai-disclosure` (`ai_generated`, the same visible-label wording, media type, model, provider, timestamp, "EU AI Act Art. 50(2)").

`GET /api/v1/ai/media/:file` serves the signed copy (public on purpose, it goes in an `<img>`; 128-bit random name; `nosniff`; cache 1 day; 404 for unknown, expired or malformed names).

**Fail-open, loudly.** If signing is impossible (engine not loadable, no key in production, download failed) generation still succeeds: the original URL comes back with `c2pa: { signed: false, reason }`, the visible label and `aiMetadata` are unaffected, and the reason is logged once per process at error level. Startup also logs an error if the flag is on but the engine or key is missing. Nothing in the response ever contains key material.

**Video.** The global edition generates no video today (the script endpoint returns a script only), so there is nothing to sign yet. `ProvenanceService.signMedia` / `attachToGeneratedMedia(..., { mediaType: 'video' })` already handle MP4/MOV (tested with a real MP4); call it from the future video endpoint the same way the image endpoint does.

**Text.** Unchanged: visible label (`[This content was generated by AI]`) plus the machine-readable `aiMetadata`. C2PA does not apply to plain text.

### Why no invisible text watermark

Statistical or character-level text watermarks (zero-width characters, token-bias schemes) are **not robust**: they disappear when text is copy-pasted through a normalizer, paraphrased, translated or screenshotted, zero-width characters are stripped by many platforms, and bias-based schemes need control of the model's sampling, which we do not have with hosted providers. Art. 50(2) asks for marking "as far as technically feasible", and for text the practical, interoperable measures are the visible label and metadata we already ship. We therefore skip invisible text watermarks. Revisit if the EU Code of Practice on marking and labelling ends up requiring a specific text technique.

## Configuration (environment only)

| Variable | Meaning | Default |
|---|---|---|
| `C2PA_ENABLED` | `true` / `false` | **on when `MARKET_REGION=global`**, off otherwise |
| `C2PA_SIGNING_CERT` | PEM certificate chain, leaf first (`\n` escapes accepted) | none |
| `C2PA_SIGNING_KEY` | PEM PKCS#8 private key for the leaf | none |
| `C2PA_SIGNING_CERT_FILE`, `C2PA_SIGNING_KEY_FILE` | paths to mounted secret files instead of inline values | none |
| `C2PA_SIGNING_ALG` | `es256` `es384` `es512` `ps256` `ps384` `ps512` `ed25519` | `es256` |
| `C2PA_TSA_URL` | RFC 3161 timestamp authority (keeps credentials verifiable after the certificate expires) | none |
| `C2PA_ALLOW_EPHEMERAL` | allow the throw-away dev certificate when no key is configured | on outside `NODE_ENV=production`, off in production |
| `MEDIA_STORE_DIR` | where signed files are kept | `./data/generated-media` |
| `MEDIA_STORE_TTL_DAYS` | retention | 30 |
| `MEDIA_PUBLIC_BASE_URL` | absolute origin for the signed-file URL (needed by the mobile apps) | relative URL |
| `C2PA_MAX_MEDIA_BYTES` | refuse to sign larger files | 26214400 |

**Keys come from configuration only. No key or certificate is in the repository** (a test scans the provenance sources for PEM private keys). In dev / tests, when nothing is configured, `ephemeral-cert.ts` generates a throw-away ECDSA P-256 CA + leaf at runtime (in memory, never written to disk, 30 days, names say "ephemeral - not for production"). Credentials signed with it are cryptographically valid but the signer is on no trust list, so verifiers show "unknown signer"; the manifest says so in the certificate name. In production without a key the API signs nothing and says so (see fail-open). Setting `C2PA_ALLOW_EPHEMERAL=true` in production is possible as an interim (the file is still marked as AI-generated, with an untrusted signer, and the key changes at every restart) but legal and the owner should decide that explicitly.

## Library and licence check

| Item | Result |
|---|---|
| Library chosen | `@contentauth/c2pa-node` 0.9.11 (Node bindings for Adobe's Content Authenticity Initiative `c2pa-rs`), in-process, no CLI subprocess. `c2patool` was the alternative; it needs a binary shipped in the image and a process spawn per file |
| Licence | **MIT** (`package.json` `license` field and the `LICENSE` file, © Adobe). Source headers state "Apache-2.0 or MIT, at your option" |
| Transitive packages added | 116, all under `optionalDependencies`, all permissive: MIT, ISC, BSD-3-Clause, Unlicense. Two have no `license` field in `package.json`: `@contentauth/c2pa-types` (its `LICENSE` file is MIT, © Adobe) and `buffers` 0.1.1 (upstream MIT). Please have the OSS review confirm those two |
| Native binary | downloaded by the package's postinstall from the project's GitHub releases (linux x64/arm64 glibc, macOS, Windows). **No musl/Alpine build** |
| Runtime requirement | Node >= 22.12 (the package is an ES module loaded with `require()`) and glibc |
| `npm audit --omit=dev --audit-level=high` | already failing before this change (11 vulnerabilities incl. 4 high, 1 critical: body-parser, multer, engine.io, proxy-addr, undici …). This change adds one moderate (a `minimatch`/`glob` chain inside the optional tree) and no high or critical finding |

Because of the glibc / Node 22 requirement:

- `runtime/api/Dockerfile` moves from `node:20-alpine` to `node:22-bookworm-slim` (apt instead of apk, `groupadd`/`useradd` instead of `addgroup`/`adduser`, `ca-certificates` added). Node 20 is end-of-life. Build arg `REQUIRE_C2PA=1` makes the image build fail if the engine cannot be loaded; use it for the global image.
- `.github/workflows/ci.yml` API job: `node-version` 20 to 22.
- The dependency is **optional and loaded lazily**, so on Node/musl where it cannot load the API still starts; it logs why and returns `c2pa.signed=false`.

## Tests

- `src/common/provenance/*.spec.ts`: config/flag defaults, fake-engine behaviour (signing request contents, fail-open paths, once-only logging, size / type / private-host guards, redirects), media store (TTL, traversal), ephemeral chain structure, and **the real library** (via `scripts/c2pa-real-check.ts`, run in plain Node because jest cannot load the ES-module + native addon): JPEG, PNG, WebP and MP4 sign, read back as AI-generated and valid, tampering invalidates, configured PEM from env is used.
- `src/modules/ai/ai-controller-c2pa.spec.ts`: the real controller and media route end to end, flag on/off per edition, fail-open.
- The real-engine specs skip themselves where the binary cannot load.
- By hand: `npx ts-node -T scripts/c2pa-real-check.ts` prints the real-library results as JSON. Any file can be inspected with the CAI tools (`c2patool file.png`, or contentcredentials.org/verify).

## Human items before go-live

1. **Get a signing certificate.** For credentials that verifiers show as trusted, the signer certificate must chain to the C2PA trust list (conformance programme). Until then use a private CA and accept "unknown signer" in viewers. Store the key in the secret manager, mount as `C2PA_SIGNING_CERT_FILE` / `C2PA_SIGNING_KEY_FILE`. Plan rotation; set `C2PA_TSA_URL` so old credentials stay verifiable.
2. **Durable media storage.** The default is a local directory (30-day TTL). With more than one API instance, or redeploys that wipe the container, mount a shared volume at `MEDIA_STORE_DIR` or replace `MediaStore` with an object-storage implementation (two methods: `put`, `get`). Signed files for already-returned URLs disappear with the directory.
3. **Image URL reach.** The URL is relative (`/api/v1/ai/media/…`). The web client works because the Next.js `/api/v1/[...path]` proxy forwards it (signed-in users). The Flutter apps need `MEDIA_PUBLIC_BASE_URL=https://<api-origin>`.
4. **Build the image once with `--build-arg REQUIRE_C2PA=1`** on the real pipeline (needs github.com access at build time) and check the startup logs show no "C2PA ... unavailable" line. The Dockerfile change was not built with Docker in this work (no Docker daemon was available); the library was verified on glibc Linux with Node 24 and Node 22.23.4.
5. **Social platforms strip metadata** on upload (most do). The credential protects the file we hand out and its downloads; it does not survive every re-upload. This is why the visible label stays.
6. Legal sign-off that C2PA + visible label meets Art. 50(2) for the global edition, and whether the CN edition should also turn the flag on.

# 规则库：自动更新与「为你推荐」（分发侠）

本文说明在「待审核规则库」（见 `待审核规则库说明.md`）之上加的两件事：规则会跟着官方文件更新；每个人看到的推荐不一样。两件事都遵守同一条底线：**没有人工审核，什么都不会上线**。

## 一、自动更新

### 怎么运行

- 代码在 `runtime/api/src/modules/library/`。`LibraryJobService` 挂在已有的自我改进（SIL）调度槽上，不另起一套定时：
  - 每天 02:00（`SIL_CRON.daily_scan`）：逐条重新抓取每条规则的官方来源，对比上次审核时的内容。
  - 每周日 03:00（`SIL_CRON.weekly_cycle`）：扫描国家机关的公开列表页，把新出现的相关文件登记为「候选」。
- 总开关 `LIBRARY_FRESHNESS_ENABLED`，**默认不开**，和 `SIL_ENABLED` 互不影响。没打开时定时任务什么都不做，命令行也会明确提示。
- 抓取限制：只许 https；只许白名单域名（`data/sources.json`，与 SIL 的 `domainOk` 同一套规则）；跳转只许留在同一域名内且最多 3 次；单页最多 2 MB；页面里带提示词注入特征的内容会被标记，不会被采信。
- 国家卫健委网站（`www.nhc.gov.cn`）拒绝程序访问（返回 412）。这类来源登记为 `manual`：**不会假装核对过**，由人在浏览器里核对，系统只按超时（90 天）提醒。

### 它会发现什么

| 检测结果 | 含义 | 用户看到什么 |
| --- | --- | --- |
| `ok` | 来源内容和审核时一致 | 「核对于 日期」，自动核对也会顺延核对日 |
| `minor_change` | 只有极少的标点/空白变化，没有数字或「修订」字样 | 同上 |
| `changed` | 内容或标题变了 | 仍可看，但挂提示「官方来源近期有更新，本条还没有对照最新版本」，**不再推荐**，不算现行 |
| `repeal_signal` | 标题或开头出现「已废止/失效」等字样，或这类字样变多 | **整条隐藏**（列表、推荐、首页卡片都不出现），直接打开链接只看到红色「不作为现行规定」说明 |
| `url_broken` / `unreachable` | 链接失效 / 暂时打不开 | 连续 3 次后挂「暂时无法访问官方来源」，不再推荐 |
| `manual` | 站点拒绝程序访问 | 只按 90 天超时提醒 |

页面里每天都会变的行（浏览量、导航、日期戳）在比较前会被去掉，所以「今天浏览量变了」不会触发任何变化。只改标题、正文不变，也算变化（标题里加「已废止」是常见做法）。

### 新文件怎么进来

周扫描只读列表页上的标题和日期。标题命中关键词（广告、直播、食品、AI、未成年人……）、来自白名单域名、此前没见过的链接，才会登记成「候选」，并且：

- 永远是「待核实」+「待审核」，**不可见**，不进推荐，不进 AI 回答；
- 带出处：列表页地址、标题、发布日期、发布机关，并写明「仅列表页标题与日期，正文未读」；
- 第一次运行只收近 45 天内的、有日期的链接，没有日期的只记为「已见」，免得把历史文章一次性灌进来。

当前登记的列表页：市场监管总局广告监督管理司（`samr.gov.cn/ggjgs/`）、国务院政策文件库（`gov.cn/zhengce/index.htm`）、国家网信办首页（`cac.gov.cn`）。第一轮人工看的重点候选方向：市场监管总局关于「提示性用语」、互联网广告生态治理、市场秩序整治重点任务的通知。这些**只是方向**，没有任何一条已被读过正文或采信。

### 审核怎么写回（人做，系统不做）

```
npx ts-node src/modules/library/cli.ts approve  <规则id> --reviewer 姓名
npx ts-node src/modules/library/cli.ts update   <规则id> --reviewer 姓名 --note "变更说明"
npx ts-node src/modules/library/cli.ts confirm  <规则id> --reviewer 姓名
npx ts-node src/modules/library/cli.ts repeal   <规则id> --reviewer 姓名 --note 原因
```

- 必须写审核人姓名，缺了就拒绝；每一步写进 `library_review_log.jsonl`。
- `approve`：待审核→已审核，记下审核人、日期、**当时来源内容的摘要**（之后来源再变就会被发现），首次上线日 `approved_at` 只写一次。
- `update`：来源变了、人读过并改好条目后，写「更新于」和**必填的更新说明**，基线换成最新来源。用户会看到「更新于 日期」和更新说明（30 天内）。
- `confirm`：人读过变化，确认对本条没有影响，续上核对日。
- `repeal`：标为已废止，用户端不再显示为现行。

定时任务**从不调用**这些函数，也不改条目文件；它只写状态文件、来源快照和一份报告（`library_report.md`，开头写明「没有任何内容因此上线」）。`POLICY_REVIEWERS` 保持为空，SIL 保持关闭。

### 展示规则（唯一一处，服务端定）

`live/display.ts` 的 `decide()` 按顺序判断：待审核（不显示）→ 已废止/被取代（不显示）→ 来源出现废止迹象（不显示）→ 征求意见稿/待核实（显示+提示，不推荐）→ 来源有变化（显示+提示，不推荐）→ 连续打不开（同上）→ 超过 90 天没核对（同上）→ 现行（显示「核对于」，近 30 天更新过的另显示「更新于」+说明）。前端不自己判断，连不上服务器时的兜底是：已废止的不出现，其余条目一律带「可能不是最新」，不显示任何「核对于」。

## 二、个性化推荐（只在应用内，不推送、不发短信、不发邮件）

### 用了什么、没用什么

只用账号自己有的信息，每条推荐都写明理由：

- 你绑定的发布平台（已绑定账号，或个人设置里的默认平台）；
- 你在「人设」里自己写的账号定位文字（说明、定位、领域、受众、话题）；
- 你关注 / 不再推荐的主题；
- 你在这里点开读过哪些规则；
- 规则库自己的变化（审核通过的更新、新增）。

不用其它租户的任何数据，不猜没写过的东西，不用位置，不收集发布内容。规则条目当前都是国家层面的，所以「平台」这一项只会对直播类（需要平台有直播功能）起作用；条目将来加了 `platforms` 字段，会按适用平台加权。

### 怎么排序

纯函数 `feed.ts`，同样输入得到同样结果（同一人同一天稳定，只在不同的人之间用日期+用户做微小的打散）：

- 你关注的主题 +5；条目标明适用的平台正是你发布的平台 +5；直播类且你的平台有直播功能 +3；账号定位里提到相关词 +3；广告标识这类所有人都要知道的 +1；读过同类 +1（上限 +2）；
- 自上次来访新增 +2（只对相关的人，否则 +1）；**更新**：只对相关的人，或点开读过旧版本的人 +3 并带「上次来访后有更新」标记；其余人 14 天内的更新 +2；只被推荐过、没点开过，不算「看过旧版」，不会被更新提醒打扰；
- 读过这一条 −6（14 天内，除非它刚更新）；最近 3 天推荐过 −1.5、7 天内 −1（只用来轮换，不压过相关度）；
- 你不再推荐的主题：不出现；不是「现行」的条目：不进推荐（`feed_eligible`）。

### 用户能做什么

- 规则库页顶部的「为你推荐」：每条显示主题、核对/更新日期、更新说明、「为什么推荐」，以及「上次来访后新增 / 有更新」标记；
- 「推荐设置」：关注 / 取消关注、不再推荐 / 恢复推荐某个主题，**总开关**（关闭后立刻不再推荐，并清掉已记录的读过/推荐过的内容，之后也不再记录）；
- 工作台首页（创作工作室）顶部一张卡：只在有新增/更新、或匹配度很高时出现，否则什么都不显示；关闭后不出现；
- 设置存在 `User.preferences.library`（不新增数据库表，账号注销时随 preferences 一起清除）。

### 接口（`/api/v1/library/*`，需登录；国际版部署下不存在）

`GET entries`、`GET entries/:id`、`GET feed`、`GET home-card`、`GET|PUT preferences`、`POST visit`、`POST opened/:id`。

「上次来访」只在用户离开页面时记录（`visibilitychange` / `pagehide`），所以本次打开页面时「自上次来访」的标记不会被自己抹掉。

## 三、测试

- `live/live.spec.ts`（16 个）：文本抽取、块对比、变化检测（含只改标题）、展示规则、审核写回、发现新文件、任务开关与受限抓取、命令行。
- `library.sim.spec.ts`（12 个）：**5 个人 × 7 天**（周一到周日），周四来源更新，周五审核。五个人分别是美妆号（小红书）、养生号（抖音）、AI 科普号（B 站）、教育号（知乎）、没有绑定任何平台的新用户。断言：每天五个人的推荐互不相同；理由和账号对得上；周四来源有变的两条当天起不再被推荐并带提示；周四来源出现废止迹象的两条所有人都看不到，周五人工标为已废止后也不是现行；全周没有任何已废止/待审核/来源有变的条目以「现行」出现；周五审核后更新的那条对相关的人和读过旧版的人带「更新」标记和说明，对无关的人没有；关闭/静音/关注生效；关闭后不再记录。
- `library.http.spec.ts`（5 个）：真实路由、登录保护、只改自己的设置、不碰 `preferences` 里的其它字段。
- `scripts/test-library-live.mjs`（7 项）：前端兜底、页面结构、全中文、接口路径与后端一致。

模拟里的「审核人」是测试里的假名字，「已审核」只存在于测试临时目录；**真实条目仍然全部是待审核**。网页和数据库是假的，抓取→对比→展示→排序→推荐这条链路是真的。

## 四、还需要人做的事

1. 人工审核待审核条目（系统不会替你审）。
2. 需要上线时在生产环境显式设置 `LIBRARY_FRESHNESS_ENABLED=1`；`POLICY_REVIEWERS` 继续留空。
3. 国家卫健委页面（`manual`）要有人在浏览器里核对。
4. 候选条目要人去读正文再决定收不收。
5. 工作台首页那张卡改了 `studio/page.tsx` 的两行，和其它改动同一文件时留意合并冲突。
